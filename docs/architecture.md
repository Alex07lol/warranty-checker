# System Architecture

## Architecture Overview

WarrantyVault follows a client-server architecture. The Flutter Android application communicates with a Node.js and Express REST API. The API interacts with MongoDB Atlas for data persistence and Cloudinary for binary file storage. JSON Web Tokens secure all authenticated endpoints.

## Layer Descriptions

### Presentation Layer (Flutter)

The Presentation Layer is built using the Flutter framework, targeting Android devices. It handles the user interface, screen navigation, state management, and all user interactions. The HTTP client (Dio) manages network requests to the REST API, including injecting authentication headers. Local storage via SharedPreferences handles persisting the JWT between sessions. The application also contains notification-handling logic to surface warranty expiry alerts and service reminders generated by the backend.

### API Layer (Node.js/Express)

The API Layer is a Node.js server running the Express framework. It exposes RESTful endpoints for the Flutter application to consume. The layer is structured with a routing tier for incoming requests, a middleware stack for cross-cutting concerns such as logging, authentication, and rate limiting, and a controller pattern to separate request handling from business logic. Request validation via Joi ensures data integrity before processing. Centralized error handling manages HTTP response codes and messages uniformly.

### Data Layer (MongoDB Atlas)

The Data Layer relies on MongoDB Atlas, a fully managed cloud database service. It uses replica sets for high availability and fault tolerance. The Express server maintains connection pooling via Mongoose to manage database connections efficiently. Mongoose provides schema definition, validation, and query building capabilities on top of the native MongoDB driver.

### File Storage Layer (Cloudinary)

The File Storage Layer uses Cloudinary for managing binary assets, specifically images and PDF documents associated with products and warranties. The Express API handles uploading files to Cloudinary using multer-storage-cloudinary, organizes them into structured folder paths, and stores the returned URL and public_id in MongoDB. Cloudinary serves these assets via its global CDN for fast and reliable retrieval by the Flutter application.

## Authentication Architecture

The system uses JSON Web Tokens for authentication. The workflow begins when a user registers or logs in. The server authenticates the credentials and issues a signed access token with a 7-day expiry. The Flutter client stores this token in SharedPreferences. For every subsequent request to a protected endpoint, the client includes the token in the `Authorization: Bearer <token>` header. The server's auth middleware intercepts these requests, validates the token signature and expiration, and attaches the decoded user payload to the request object before passing control to the controller.

## Security Architecture

- All client-server communication is over HTTPS.
- JWT tokens expire after 7 days, limiting the impact of a leaked token.
- User passwords are hashed with bcrypt using a cost factor of 12 before storage. Plaintext passwords are never persisted.
- Input sanitization is enforced on all API endpoints to mitigate NoSQL injection attacks.
- Rate limiting is applied to authentication endpoints to prevent brute-force attacks.
- CORS is configured to allow only expected origins.
- All secrets and credentials are loaded from environment variables and never committed to the repository.
- Cloudinary upload operations are handled server-side so API credentials are never exposed to the mobile client.

## Data Flow: Document Upload

1. The user selects a file in the Flutter application using the image picker or file picker.
2. The Flutter application attaches the file as multipart form data to an authenticated POST request.
3. The HTTP client sends the request with the JWT in the Authorization header to the Express API.
4. The Express auth middleware validates the token and attaches the user to the request.
5. The Joi validation middleware validates the document type and metadata fields.
6. The multer-storage-cloudinary middleware streams the binary file to Cloudinary.
7. Cloudinary processes the upload and returns a secure URL and public_id.
8. The document controller constructs a new document record with the Cloudinary URL, public_id, file metadata, productId, and userId.
9. Mongoose saves this record to the `documents` collection in MongoDB Atlas.
10. The API responds to the Flutter application with status 201 and the created document object.

## Deployment Architecture

The Day 2 target is local development. The Node.js backend runs locally, connecting to a MongoDB Atlas free tier cluster. The Flutter application is compiled as a debug APK and installed directly on an Android device or emulator for testing.

Post-buildathon deployment path:

- Backend: deployed to Railway or Render using a connected GitHub repository.
- Database: MongoDB Atlas M0 free tier for development, M10+ for production.
- File storage: Cloudinary free tier for development, paid plan for production.
- Mobile: APK distributed directly for buildathon demonstration; Play Store submission as a future milestone.

## Scalability Considerations

The architecture is designed to scale horizontally without structural changes.

- The Express server is stateless, making it suitable for horizontal scaling behind a load balancer.
- MongoDB Atlas supports automated scaling to higher tiers and sharding for large datasets.
- Cloudinary's CDN offloads media delivery entirely from the primary application server.
- JWT authentication eliminates server-side session storage, meaning any API instance can validate any request independently.
- Mongoose connection pooling is configurable to handle increased concurrent database connections at higher traffic levels.
